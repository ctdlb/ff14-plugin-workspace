## ③ 五个问题

### 3.1 opcode 数据怎么用

**目录结构：按「区域_客户端版本」一个目录一份快照，旧版本一律不删。** `output/` 下共 74 个目录（44 个 CN，从 `CN_2022.11.01` 到 `CN_2026.10.06`，另有 Global/KR）。目录名是脚本拼出来的：`f"{Region}_{BuildID}"`，不存在就新建 —— `KO/ffxiv_opcode_finder.py:1408-1416`；`OutputPath` 就是脚本旁的 `output/`（`KO/ffxiv_opcode_finder.py:19-22`）。

每个版本目录里 5 个文件（`KO/output/CN_2026.10.06/`），都是一次运行同时写出的（`KO/ffxiv_opcode_finder.py:1418-1429`、`:1460`）：

| 文件 | 形态 | 谁用 |
| --- | --- | --- |
| `opcodes.json` | `{"version","region","consts":{...},"lists":{"ServerZoneIpcType":[{"name","opcode"}...],"ClientZoneIpcType":[...]}}`，opcode 是**十进制** | 给人和给程序读的对外格式（`KO/output/CN_2026.10.06/opcodes.json`；`ClientZoneIpcType` 从 `:589` 开始） |
| `opcodes_internal.json` | 同样字段，但 `lists` 下是**字典** `"ServerZoneIpcType": {"PlayerSpawn": 613, ...}` | 给同仓库的生成器（`Ipcs_cn.cs` / `lemegeton.xml` / `machina.txt`）喂数据（构造函数见 `KO/ffxiv_opcode_finder.py:1393-1406`） |
| `Ipcs_cn.cs` | `// Generated by https://github.com/gamous/FFXIVNetworkOpcodes` + `namespace FFXIVOpcodes.CN` 下的 4 个 enum（十六进制字面量，如 `PlayerSpawn = 0x0265`） | 直接丢进 C# 工程当查表用（`KO/output/CN_2026.10.06/Ipcs_cn.cs:1-3`） |
| `lemegeton.xml` | 多区合并的 Blueprint 片段 | Lemegeton / Machina 系解析器 |
| `machina.txt` | `Name\|HEX` 行文本（`PlayerSpawn\|265`） | Machina 解析器 |

**`enum.json` 不是 opcode 表**，它只有两个键：`ActorControlType`（`KO/output/enum.json:2`）与 `ActionEffectType`（`KO/output/enum.json:183`）——是**包体里的子类型枚举**（`ActorControl` 的 category、`ActionEffect` 的 type），带人工注释（`KO/output/enum.cs` 里 `Death = 6, // dissector calls it DefeatMsg`）。查 opcode 别看它，查「这个 ActorControl 的 6 是什么意思」才看它。

**`meta.json` 已停更**：全文件只有 8 条 `ver_id`，最新到 2023 年，没有 `CN_2026.10.06` 这类新条目（`KO/output/meta.json`）。当版本索引会踩空。

**Dalamud 插件里怎么拿 opcode：作者没给示例，只能自己拼。** FFXIVNetworkOpcodes 仓库里**没有任何 C# 工程**（根目录只有 `*.py`、`lemegeton.xml`、`machina.template`、`signatures.json`、`README.md`、`NAME.md` 和 `output/`、`script/`），所以「插件里怎么用」得自己接：把 `Ipcs_cn.cs` 这个 enum 放进工程，按包名取值即可。

**怎么 hook 收发包：本机 Dalamud 自带的「网络监视器」就是最干净的实证配方**（中文文案说明这是国服分支）：

- 收包（ZoneDown）：`Hook<PacketDispatcher.Delegates.OnReceivePacket>.FromAddress((nint)PacketDispatcher.StaticVirtualTablePointer->OnReceivePacket, this.OnReceivePacketDetour)` —— `KB/Dalamud/Dalamud/Interface/Internal/Windows/Data/Widgets/NetworkMonitorWidget.cs:64-66`
- 发包（ZoneUp）：`Hook<ZoneClient.Delegates.SendPacket>.FromAddress((nint)ZoneClient.MemberFunctionPointers.SendPacket, this.SendPacketDetour)` —— 同文件 `:68-70`
- detour 里取 opcode 的位置差 2 字节，**这是最容易接错的一处**：
  - 收包 `var opCode = *(ushort*)(packet + 2);` —— 同文件 `:221`
  - 发包 `var opCode = *(ushort*)packet;` —— 同文件 `:229`
  - 之后照常调原函数（`OriginalDisposeSafe`，`:224`、`:231`）
- 结构侧支撑：`PacketDispatcher` 是带虚表的 interop 结构（`KB/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Client/Network/PacketDispatcher.cs:12-13`），`NetworkModule` 里挂着 `PacketReceiverCallback`（`KB/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Application/Network/NetworkModule.cs:42`），`NetworkModuleProxy` 反查 `NetworkModule`（`KB/FFXIVClientStructs/FFXIVClientStructs/FFXIV/Client/Network/NetworkModuleProxy.cs:10-11`）。

> 注意两件事：① Dalamud 本体是 **AGPL-3.0**（`KB/Dalamud/LICENSE:1-2`），上面那几行要**照结构自己重写**，不要整段复制进自己仓库；② `PacketDispatcher.StaticVirtualTablePointer->OnReceivePacket` 这种取法依赖 FFXIVClientStructs 的代际，升级时要重新对一遍。

### 3.2 opcode 数字从哪来、游戏更新后怎么补

**来源不是抓包，是 IDA 里的静态分析 + 一份跨区签名库。**

- `signatures.json` 是核心资产：按 `ServerZoneIpcType` / 其他 IpcType 分组，**每个包一条**，每条可以给 `Global`/`CN`/`KR` 三份字节签名（`KO/signatures.json:2-7`），还允许附 `Comment`（人工找法，如"Search for 48 ? ? 44 88 40 ? 89 48 and goto second xref"）与 `Type`（`Call` / jmptable 之类，见 `KO/signatures.json:9-16` 的 `EffectResult` 条目）。
- 提取脚本 `ffxiv_opcode_finder.py`（60KB）读这份签名库并按当前区域挑对应那一列：`KO/ffxiv_opcode_finder.py:1028`（读 `signatures.json`）、`:1052-1063`（`Region == "CN"` 时取 `sig["Signature"]["CN"]` 或 `sig["CN"]`）。
- **区域和版本号是自动识别的，不靠手填**：先从 exe 里的 `/*****ff14******rev` 串取出 `BuildID` 与 `VersionID`（`KO/ffxiv_opcode_finder.py:36-40`），再从 pdb 路径段判断区服 —— `shanda`→CN、`ver`→Global、`actoz`→KR（`:41-58`）。
- 识别 opcode 的三条路径（`KO/README.md:17-21`）：jmptable switch 里带特定 case、普通 switch 里的变参调用、以及「任何对 `ZonePacket` 发送函数的调用」；用法是 IDA 里 `Alt+F7` 直接跑，无需配置（`KO/README.md:3-11`）。
- **更新后的补法**（源码+文档能证实的一半）：换新客户端 → 新 exe 里签名会有一批失配 → 失配信息落在 `errors.json`（`KO/ffxiv_opcode_finder.py:1426`）与 `debug.json`（`:1427`），这两个文件被 `.gitignore` 忽略（`KO/.gitignore:1-2`）所以仓库里看不到 → 人工补签名（README 明确邀请贡献签名：`KO/README.md:13`）→ 重跑 → 提交新版本目录。副本录像机专用的 opcode 另有 `record_opcode_finder.py`，其输出 `opcodes_record_raw.json` 还需人工修成 `opcodes_record.json`（`KO/README.md:29-39`）。
- 仓库**没有任何 CI/工作流**（`ls -a` 只有 `.git`、`.gitignore`、`*.md`、`*.py`、`lemegeton.xml`、`machina.template`、`output/`、`script/`），所以整条链是「本地跑 IDA → commit 生成物」的手工流程（**推测**：每次客户端更新一次提交，commit message 形如 `CN 2026.10.06 7.57`；因为本机是 `--depth 1`，多版本历史未确认）。
- 自检口径写在代码注释里：`KO/ffxiv_opcode_finder.py:1099` 一行记录 *"Method (validated on CN 2026.06.18 / 7.51h2 -> 110)"* —— 即**拿「识别出的 opcode 总数」当对账指标**。
- 另外 `update_lemegeton.py` 只做汇总：扫 `output/` 取三区各自最大版本目录（`KO/update_lemegeton.py:8-24`），把三份 `lemegeton.xml` 拼成一个多区 `<Blueprint>`（`:28-40`）。

**对我们「以后自己维护一份」可借鉴的四点**：① 数据即真源，**每版一个目录、永不覆盖**（版本回溯不用 git）；② **签名库与提取脚本分离**，签名可外部贡献、每条带「怎么找」的注释；③ 一份数据生成多目标格式（C#/JSON/Machina/Lemegeton），消费者换语言也不用改数据；④ 用「计数」这种便宜指标做回归（`:1099`）。

### 3.3 Browsingway：外部浏览器画面怎么进游戏

三个程序集：`Browsingway/`（Dalamud 插件）、`Browsingway.Common/`（IPC 协议 + FlatBuffers schema）、`Browsingway.Renderer/`（**独立 exe**，CefSharp 离屏 Chromium）。

**进程间通信**：不是 HTTP/socket，是 `SharedMemory` 包的 `RpcBuffer`（命名共享内存上的请求/响应），消息体用 FlatSharp 序列化：

- `Browsingway.Common/IpcBase.cs:11-27` —— `private readonly RpcBuffer _buffer;`，构造时 `new RpcBuffer(name, (msgId, data) => { HandleCall(RpcCall.Serializer.Parse(data)); })`；发送侧序列化后 `await _buffer.RemoteRequestAsync(buffer[..bytesWritten])`。
- 通道名带 pid，避免多开冲突：`BrowsingwayRendererKeepAlive{pid}` / `BrowsingwayRendererIpcChannel{pid}` —— `.tmp/study/Yarukon/Browsingway/Browsingway/RenderProcess.cs:42-43`。
- 双向 RPC 契约：渲染进程→插件 `RendererReady`/`SetCursor`/`UpdateTexture`（`Browsingway.Common/BrowsingwayRpc.cs:9-12`）；插件→渲染进程 `NewOverlay`/`Navigate`/`ResizeOverlay`/`InjectUserCss`/`Zoom`/`Mute`/`Debug`/`RemoveOverlay`/`MouseButton`/`KeyEvent`（第 `:15-63`）；渲染侧镜像 `Browsingway.Common/RendererRpc.cs:9-18`。

**纹理上传：D3D11 共享纹理句柄，不是读像素再 `ImGui` 上传。** 这是全篇最值得抄的思路：

1. 插件侧拿游戏自己的设备：`_device = (ID3D11Device*)pluginInterface.UiBuilder.DeviceHandle;`，`WindowHandle = pluginInterface.UiBuilder.WindowHandlePtr;` —— `Browsingway/DxHandler.cs:14-19`；再 QueryInterface 出 `IDXGIDevice` → `GetAdapter` → 记下 `AdapterLuid`（`:47`）。
2. 渲染进程按 LUID 找**同一块 GPU** 再建设备：`CreateDXGIFactory1` 枚举适配器比对 HighPart/LowPart（`Browsingway.Renderer/DxHandler.cs:15-38`），`D3D11CreateDevice(gameAdapter, D3D_DRIVER_TYPE_UNKNOWN, ..., D3D11_CREATE_DEVICE_BGRA_SUPPORT)`（`:64-74`）。
3. 建共享纹理：`Format = DXGI_FORMAT_B8G8R8A8_UNORM`、`Usage = D3D11_USAGE_DEFAULT`、`BindFlags = D3D11_BIND_SHADER_RESOURCE`、`MiscFlags = isShared ? D3D11_RESOURCE_MISC_SHARED : 0`（`Browsingway.Renderer/TextureRenderHandler.cs:318-343`）；句柄用 `IDXGIResource::GetSharedHandle` 导出（`:48-68`）。
4. CEF 的 `OnPaint` 把 32bpp BGRA 缓冲 `UpdateSubresource` 到内部纹理、`CopySubresourceRegion` 合成到共享纹理、再叠 HTML 弹出层、`Flush()`（`:108-206`）。
5. 句柄经 RPC 回传（`Browsingway.Renderer/Program.cs:106-120` → `Plugin.cs:114-128`，并切回框架线程 `Services.Framework.RunOnFrameworkThread`），插件侧 `device->OpenSharedResource((HANDLE)handle, &texture2DGuid, &texturePtr)`（`Browsingway/SharedTextureHandler.cs:28`）→ `CreateShaderResourceView`（`:49`）→ `_textureId = new ImTextureID((nint)_view)`（`:58`）→ 画 `ImGui.Image(_textureId, _size)`（`:69`）。

**坐标/尺寸同步：靠「每帧比大小」而不是事件。** `HandleWindowSize()` 每帧读 `ImGui.GetWindowContentRegionMax() - GetContentRegionMin()`，与记录值不同就发 `NewOverlay`（首次）或 `ResizeOverlay(guid, w, h)`，并置 `_resizing` 防抖 —— `Browsingway/Overlay.cs:304-331`（分支在 `:311-322`、`:326`）。全屏时还要补 1px：`fsPos = screen.WorkPos - 1`，注释写明「ImGui always leaves a 1px transparent border」（`:125-142`）。窗口 ID 用 `$"{Name}###{Guid}"` 固定（`:123`），否则重命名会换 ImGui 状态。

**输入回灌**：鼠标坐标换算成窗口内相对坐标（`io.MousePos - windowPos - GetWindowContentRegionMin()`，`Overlay.cs:238`）后打包成 `MouseButton` RPC；**透明像素穿透在渲染进程侧判定** —— 从 `_alphaLookupBuffer` 取 BGRA 第 4 字节，`alpha == 0` 时切换光标模式（`Browsingway.Renderer/TextureRenderHandler.cs:295-316`、`:352-366`）。键盘走 Win32 窗口子类化：`SetWindowLongPtr(hWnd, GWL_WNDPROC, _detourPtr)`（`Browsingway/WndProcHandler.cs:18-25`、`Browsingway/NativeMethods.cs:39-43`），detour 只认自己的 hWnd、`(bool, long)` 第一项为 true 表示吞掉消息（`WndProcHandler.cs:40-55`），还原前先比对当前过程指针是否仍是自己（`:32-37`，注释提到可能被 InterfaceManager 抢先清理）；WM_KEY\* → `KeyEvent` RPC（`Overlay.cs:82-112`）。

**进程生命周期**：父进程退出子进程要自杀——子进程建 `EventWaitHandle(args.KeepAliveHandleName)` 后 `WaitOne()` 阻塞（`Browsingway.Renderer/Program.cs:46-50`、`:66`），父进程 `Stop()` 里 `Set()` + `WaitForExit(1000)` + `Kill()`（`RenderProcess.cs:147-162`）；崩溃自动重启上限 5 次（`RenderProcess.cs:79-145`，`_maxRestarts = 5`）；子进程 `DOTNET_ROOT` 被强制指向 Dalamud 自带运行时（`:224-226`）。

**取舍（这才是对我们有意义的部分）**：

| 取舍点 | 它怎么选 | 代价 / 风险 |
| --- | --- | --- |
| CEF 体积 | **不进插件 zip**，首次启动从作者自己的 OSS 域名下 zip 并校验 SHA256（`Browsingway/DependencyManager.cs:44`，解到 `ConfigFile.DirectoryName/dependencies`，`:55`） | 依赖 `oss.yarukon.me` 的可用性与信任（供应链风险）；首次要下几百 MB；离线/国内网络容易卡在下载条 |
| GPU | 必须与游戏同一块显卡（LUID 匹配，`Renderer/DxHandler.cs:38`） | 笔记本双显卡/独显直连切换时会失败；作者 README 明确**不支持 Linux**，因为跨进程纹理传输依赖 D3D11 共享句柄 |
| 帧率 | 每个悬浮窗独立 `WindowlessFrameRate`（`Browsingway.Renderer/Overlay.cs:81`），渲染进程每帧还有 `EnsureRenderProcessIsAlive()`（`Plugin.cs:211-224`） | 一个浏览器窗口 ≈ 一个持续渲染的进程；多开窗口就是多份 CEF 负载 |
| 外挂边界 | **完全不 hook 游戏函数、不读写游戏内存、不碰网络协议**——全仓库 grep 无 `Dalamud.Hooking` / `SendPacket` / `SigScanner`；只用 `UiBuilder.DeviceHandle` / `WindowHandlePtr` + 自绘 ImGui 窗口 + Win32 窗口子类化（`Browsingway/WndProcHandler.cs:18-25`） | 唯一「灰色」的是键盘消息被插件吞掉/转发，以及内嵌浏览器能登录任意网站（钓鱼、多开窗口的社交风险）。技术上它不构成「进程注入/改包」那类判断依据 |

> 结论：想在游戏里显示自定义内容，**首选进程内 ImGui 自绘 + 本地取数据**；只有真的需要 HTML 排版（地图、富文本页面）才值得走它这条路，那时「渲染进程 + 共享纹理句柄 + 每帧比大小同步」是唯一正确姿势，别自己发明像素回读。

### 3.4 Physis / Kawari 怎么组织包结构定义

**Kawari：`opcodes.yml` 单一真源 → `build.rs` 生成 Rust enum + Markdown 表。**

- 数据：`resources/data/opcodes.yml`（1451 行），按 IpcType 分组，每个包四行——名字、一句话 `comment`、`opcode`、`size`：
  `- name: ZoneInit` / `comment: Inform the client which zone to load, ...` / `opcode: 929` / `size: 136` —— `.tmp/study/Yarukon/Kawari/resources/data/opcodes.yml:1-5`（`size` 是**线上定长**，不是估算）。

**有没有比 FFXIVClientStructs 更适合查字段的地方？分用途，见下表。**

| 你要查 | 该用哪个 | 依据 |
| --- | --- | --- |
| 线上包的字节布局、字段语义、包定长大小、某个 opcode 当前叫什么 | **Kawari 的 `core/src/ipc/**/*.rs` + `resources/data/opcodes.yml`**（73 个包文件、字段带 Excel 表名与注释） | `resources/data/opcodes.yml:1-5`；`core/src/ipc/zone/server/zone_init.rs:45-80` |

覆盖度对比（实测文件数）：Kawari 73 个包定义 vs FFXIVClientStructs 18 个 `*Packet.cs`；所以「查一个冷门包」Kawari 命中率高得多，但它是**按线上字节**写的，字段偏移不能直接拿去读内存。

**Physis 与我们用 EXDViewer 的差别**：Physis 是**库**，把 sqpack→index→dat→excel 整条链做成可编程 API（`SqPackResource` → `read` / `parsed::<T>`），面向批量读写、mod 工具、服务器；EXDViewer 是**现成查看器 + 本机 MCP**，面向「查一行、几十行」。两者不冲突：本机已用 EXDViewer 查单行、`tools/item-scan` 做全表筛选，Physis 的价值只在我们需要**非 Excel 资源**（MDL/TEX/图层/LGB）或**写回**时才出现；它是 Rust + GPL-3.0，只能当参考实现看。

### 3.5 对我们（国服 Dalamud 插件、只改 UI 为主）真的有用吗

| 东西 | 判定 | 理由 |
| --- | --- | --- |
| `output/CN_<最新>/opcodes.json` | **有用** | 要「按包名查当前国服 opcode」时直接读，别自己记数字；版本目录本身就是历史对照表 |
| 网络监视器式「收/发各一条 hook」 | **有用**（若要做读包驱动 UI 的插件） | 结构性配方完整：`NetworkMonitorWidget.cs:64-70` + opcode 偏移 `:221`/`:229`；照自己重写，别整段复制（Dalamud 是 AGPL） |
| Kawari 的包定义当「包字段字典」 | **有用** | 查冷门包字段语义/大小比 FFXIVClientStructs 全，且带 Excel 表名，直接能转成 EXDViewer 的查询目标 |
| Browsingway 的「进程外渲染 + 共享纹理」 | **仅当真要嵌 HTML/网页时有用** | 纯 UI 需求用它属过度设计（CEF 下载、单 GPU、多进程负载） |
| `Ipcs_cn.cs` / `enum.cs` 连文件拷进仓库 | **不要** | opcode 仓库**无 LICENSE**（除 `.git` 外只有 `.gitignore`/`README.md`/`NAME.md`/脚本/`output`/`script`，GitHub license 字段为空）→ 拷代码进公开发布仓库有合规风险；opcode 数字是事实，自己转写成表即可 |
| Kawari / Physis 本体 | **用不上** | AGPL-3.0 / GPL-3.0，且一个是服务器模拟器、一个是数据读写库；「只改 UI」两端都用不到，搭环境只会引入无关依赖 |
| 抓包/改包路线（Chronofoil 抓 `.cfcap`、Firewall 插件屏蔽包） | **明确别做** | Kawari 自己的文档都警告「可能被视为作弊，别在有价值的账号上试」（`docs/src/packets/tips.md:30-37`）；且与 UI 需求无关 |
| `lemegeton.xml` / `machina.txt` / `opcodes_internal.json` | **用不上** | 面向 Machina / Lemegeton 解析器的格式，我们直读 `opcodes.json` 就够 |

## ④ 对我们有用的三件事 / 明确用不上的

**有用的三件事**

1. **把「当前国服 opcode」当外部数据查，而不是当常量记**：`KO/output/CN_<version>/opcodes.json` 是现成的包名→十进制 opcode 表，`Ipcs_cn.cs` 是同一份数据的 C# 形态（`KO/output/CN_2026.10.06/Ipcs_cn.cs:1-3`）。要查某个包，先读 JSON 再对名字。
2. **要做「读包做 UI」的插件，直接照 Dalamud 网络监视器的两条 hook 结构写**（收 `PacketDispatcher.OnReceivePacket`、发 `ZoneClient.SendPacket`），opcode 偏移别搞混：收包 `packet+2`、发包 `packet+0`（`NetworkMonitorWidget.cs:221`、`:229`）。名字映射回 `opcodes.json` 即可读。
3. **查包字段语义去翻 Kawari 的 `core/src/ipc/zone/server/*.rs`**（73 个包、字段带 Excel 表名注释、`opcodes.yml` 里有定长 size），比在 FFXIVClientStructs 里找 `*Packet.cs` 命中率高；反过来查内存偏移才用 FFXIVClientStructs。

**明确用不上的**

- **Kawari 本体**：AGPL-3.0 的服务器模拟器，跑它要自建服务端；与我们「国服客户端里改 UI」没有交集。
- **Physis 整体**：GPL-3.0、Rust、面向资源批量读写；查数据我们用 EXDViewer + `tools/item-scan` 已够，只有需要解析 MDL/TEX/LGB 时才回来看它的实现。
- **Browsingway 的 CEF 依赖链**：`DependencyManager.cs:44` 从作者自建域名下 Chromium 包，属于「为了一个悬浮窗引入几百 MB 外部二进制 + 供应链信任」，纯 UI 需求完全不必。
- **抓包/改包工具链**（Chronofoil、Firewall、replay_updater）：风险与收益都不在我们这边。
- **`Ipcs_cn.cs` 原文件直接进仓库**：无 LICENSE，合规上说不清；自己按 `opcodes.json` 生成自己的表。

## ⑤ 结论可信度

**源码实证（本笔记标了 `文件:行号` 的全部内容）**

- opcode 目录命名与生成逻辑、5 个产物文件、`enum.json` 只有两个子类型枚举、`meta.json` 停更：`KO/ffxiv_opcode_finder.py:1408-1429`、`:1393-1406`、`:1460`、`KO/output/enum.json:2`/`:183`、`KO/output/meta.json`。

- Dalamud 侧两条 hook 与 opcode 偏移：`KB/Dalamud/Dalamud/Interface/Internal/Windows/Data/Widgets/NetworkMonitorWidget.cs:64-70`、`:219-232`。
- Browsingway 的 IPC / 共享纹理 / 尺寸同步 / 输入回灌 / 进程保活：3.3 节引的每一处行号；「无 hook、无协议访问」由全仓库 grep（`Dalamud.Hooking`/`SendPacket`/`SigScanner` 零命中）证实。

**推测（不可当结论用）**
