# 代码结构维护

适用于本工作区的插件仓库（目前是 `TextToTalkCN` 与 `Jiage`，以及以后新建的插件）。
目标不是「追求理想架构」，而是让改动小、可回滚、后来的人（包括 AI）能看懂。

## 改之前

1. 先读再改：读目标文件，再看它的调用方与被调用方，确认项目里已有的封装。
2. 有现成写法就用现成写法：上游或项目里已有的辅助方法优先，不另造一套。
3. 不确定归属时，把新文件放到语义最近的既有目录，而不是新建一层 `Services/Utils/Helpers`。

## 改的时候

- 融入现存结构：不为单一功能引入新架构、新抽象层或事件总线。
- 一个文件一个职责：文件变长且混入第二件事时，才按既有惯例拆分。
- 状态集中：配置项进 `Configuration` 类，运行期缓存进字段；不散落全局静态变量。
- 依赖方向单向：UI 不直接做网络/文件 IO，走服务类；服务类不反向引用 UI。
- 错误处理不吞异常：`catch` 后要么记日志，要么回滚到可用状态（如后端创建失败回退）。
- 注释掉的死代码直接删；确认无引用的方法、字段、本地化键一并删。
- 顺手做的收敛只限本次触及的代码：统一命名、去重复工具方法、补必要的空值判断。

## 不做的

- 不做与本次任务无关的搬文件、批量重命名、格式大改。
- 不改上游文件的代码风格（缩进、换行、using 排序）来「统一」。
- 不引入新依赖；确实需要时先说明理由与体积影响。
- 不为了「以后可能用到」预留抽象。

## 提交

- 一次提交只做一件事；提交前确认 `git status` 只含本次相关文件。
- 提交信息 Angular 风格：`<type>(<scope>): <subject>`，body 用中文写清为什么改、怎么解决、有无副作用。
- 需要用户验收的改动，说明里覆盖：实际改动范围、兼容性影响、验收要点、未执行的验证。

## 自查清单

- [ ] 新代码放在最合适的既有位置，没有多余的分层
- [ ] 没有留下死代码、调试输出、临时文件
- [ ] 配置项与运行期状态各归其位
- [ ] 异常路径有日志或回滚，不会把插件卡死
- [ ] 只改了本次需要改的文件
- [ ] 变更说明与实际改动一致，没有谎报验证
